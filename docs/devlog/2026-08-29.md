## T24/T25 — Heartbeat OpenClaw + Brief Harian Telegram

Task paling menantang sejauh ini karena bergantung penuh pada verifikasi hidup ke binary
OpenClaw 2026.7.1, bukan sekadar membaca dokumentasi.

### Infrastruktur yang dibangun lebih dulu (prasyarat yang tidak terlihat di plan)

Sebelum menyentuh heartbeat sama sekali, ditemukan gap arsitektur: agent OpenClaw berjalan di
Docker, sedangkan seluruh kode `siaga/` ada di host Windows. Tanpa perbaikan ini, heartbeat tidak
akan pernah bisa menjalankan `scripts/run_pipeline.py` sama sekali.

1. **Bind mount repo** — `run_openclaw.sh`/`.ps1` sekarang me-mount `siaga/` ke
   `/workspace/siaga` di dalam container. Live-edit di host langsung terlihat di container.
2. **Bootstrap pip tanpa root** — image OpenClaw tidak punya `pip` maupun `ensurepip` (venv tidak
   bisa dibuat). Apt butuh root dan lambat (~90 detik network). Solusi: `get-pip.py --user
   --break-system-packages`, tanpa root, ~5 detik. Dijalankan **setiap start container**, bukan
   sekali — `/home/node/.local` tidak ada di volume manapun, hilang tiap container dibuat ulang
   (termasuk nanti migrasi VPS T10).
3. **`requirements.txt`** dibuat (psutil, jsonschema, python-dotenv) — sebelumnya cuma dependensi
   implisit tak tercatat.

Ketiganya diverifikasi dengan resimulasi dari nol: `docker rm -f` lalu jalankan skrip apa adanya,
buktikan dependency terpasang dan `run_pipeline.py` benar-benar tereksekusi dari dalam container
tanpa satu pun langkah manual tambahan.

### Drift dokumentasi OpenClaw — dicatat karena "baca dulu" saja tidak cukup

CLAUDE.md mewajibkan baca dokumentasi resmi sebelum menulis konfigurasi OpenClaw. Sudah dilakukan
(fetch `docs.openclaw.ai/gateway/heartbeat` dan `/channels/telegram`) — tapi dokumentasinya sendiri
ternyata **drift dari binary 2026.7.1 yang sungguhan terpasang**:

- **`HEARTBEAT.md` legacy**, sesuai docs, "tidak dibaca lagi saat runtime" — instruksi heartbeat
  sekarang dari "monitor scratch" database. Tapi `openclaw cron scratch <jobId>` yang disebut docs
  sebagai cara mengelolanya **tidak ada di `cron --help` binary ini**.
- **`heartbeat.target: "owner"`** — docs bilang ini nilai default. Binary menolaknya:
  `unknown heartbeat target: owner`, dan gateway **crash-loop** sampai breaker internal
  men-suppress auto-start channel Telegram (perlu restart bersih untuk pulih).
- **`heartbeat.prompt`** — docs bilang field ini meng-override prompt default. Diverifikasi lewat
  `sessions export-trajectory` (bukan cuma dibaca dari config, tapi ditelusuri ke payload
  sungguhan yang dikirim ke model): prompt kustom **tidak pernah sampai**. Model hanya menerima
  string generik `"[OpenClaw heartbeat poll]"`.

**Keputusan:** tinggalkan `agents.defaults.heartbeat` shorthand sepenuhnya (`every` di-set ke
`"0m"` — nonaktif, dibiarkan terlihat di config, bukan dihapus diam-diam). Pindah ke
**`openclaw cron add`** — fitur inti yang jauh lebih matang dan terdokumentasi eksplisit lewat
`--help` yang benar-benar cocok dengan perilakunya: `--cron "0 7 * * *" --tz Asia/Jakarta`,
`--message` (payload agent turn sungguhan, LLM tetap memutuskan — bukan command job pasif, supaya
klaim "agent bekerja proaktif" di plan/01 tetap jujur), `--tools exec` (jaminan akses shell),
`--timeout-seconds`.

### Bukti mekanisme bekerja — bukan klaim, ditelusuri sampai ke tool call

Dua putaran uji cepat (interval 5 menit) sebelum menetapkan jadwal produksi:

1. **Sesi heartbeat generik (05:01, 05:06 UTC)** — dua tick tepat 5 menit terpisah, keduanya
   memanggil LLM sungguhan (status 200, ~4-5 detik). Membuktikan penjadwal bekerja otonom. Tapi
   `sessions export-trajectory` menunjukkan model cuma menjawab `HEARTBEAT_OK` karena prompt
   kustom tidak sampai (lihat di atas) — inilah yang mengarahkan pindah ke `cron add`.

2. **Cron job uji (`siaga-daily-cycle-test`)** — tiga iterasi, masing-masing bug ditemukan lewat
   `cron runs --id <id>` yang mencatat **ringkasan diagnosis buatan agent sendiri**, bukan cuma
   exit code mentah:
   - Iterasi 1: exit 127, `~/.local/bin/python3` tidak ada (salah tulis, seharusnya `python3`
     biasa dari `/usr/bin/python3`). Agent mendiagnosis persis dan menyarankan perbaikannya.
   - Iterasi 2: exit 2, `--limit 300` bukan flag yang didukung `run_daily_cycle.py`. Agent
     mendiagnosis lagi, **dan secara eksplisit tidak mengubah apa pun sendiri** — menunggu
     konfirmasi ("Saya belum menjalankan versi itu maupun mengubah cron — beri tahu kalau mau
     saya lakukan"). Perilaku menahan diri yang tepat.
   - Iterasi 3: path benar, flag benar — proses berjalan tapi lambat (lihat temuan performa di
     bawah), bukan gagal.

Job uji dihapus (`cron rm`) setelah mekanismenya terbukti; job produksi
(`siaga-daily-cycle`, `0 7 * * * @ Asia/Jakarta`) dibuat terpisah dengan command final.

### Bug nyata ditemukan lewat proses ini (bukan cuma di-review, tapi diverifikasi eksekusi)

1. **Crash Unicode di `run_daily_cycle.py`** — sama persis kelas bug T22 (`summary_ratio()`),
   kali ini emoji 🔎 di `daily_brief.py` bikin `print()` crash di konsol Windows cp1252, SETELAH
   pipeline dan campaign clustering selesai dan tersimpan (tidak ada data hilang, cuma langkah
   print terakhir gagal). Diperbaiki: `sys.stdout.reconfigure(encoding="utf-8")` di awal skrip,
   bukan menghapus emoji dari isi brief (emoji itu memang bagian dari format Telegram-nya, sesuai
   plan/02).

2. **Test isolation bug** — `test_send_message_missing_token_raises` gagal karena `lib/llm.py`
   memanggil `load_dotenv()` di level import, membocorkan `TELEGRAM_BOT_TOKEN` asli ke seluruh
   proses pytest begitu modul lain meng-import `lib.llm` lebih dulu. Diperbaiki di sisi test
   (`monkeypatch.delenv`), bukan menghapus `load_dotenv()` dari `llm.py` — itu memang perlu untuk
   pemakaian skrip mandiri.

3. **Kontensi kunci SQLite lintas host↔container** — proses `run_daily_cycle.py` yang dijalankan
   manual di host (uji penuh backlog 13.534 domain, `--allow-network`, durasi 2437 detik) sempat
   membuat pembacaan dari dalam container gagal dengan "disk I/O error" transien. Bukan korupsi
   (integrity_check tetap `ok`), tapi caveat operasional nyata: **jangan jalankan skrip yang
   menulis `siaga.db` dari host dan container secara bersamaan** di Windows — kemungkinan besar
   lebih stabil di VPS Linux native nanti (T10), tapi belum diverifikasi.

4. **Performa `find_similar()` (T16) belum diukur pada skala harian nyata** — 39ms/domain × 213
   watchlist entri. Untuk volume harian normal (~6.500 domain), Tahap 1 sendiri makan waktu
   ~4-5 menit. Masih jauh di bawah `timeoutSeconds: 1800` yang di-set, jadi **tidak memblokir
   produksi** — tapi ini kandidat optimisasi (kemungkinan permutasi terarah dibangkitkan ulang
   untuk tiap pasangan domain×brand tanpa early-exit murah lebih dulu). Dicatat untuk nanti,
   sengaja tidak diotak-atik sekarang karena di luar lingkup T24/T25 dan berisiko regresi tanpa
   test tambahan.

### Hasil operasi nyata dari uji backlog penuh (bonus, bukan tujuan utama)

Uji `run_daily_cycle.py --date 2026-08-28 --no-llm --skip-send` (network aktif) terhadap 13.534
domain backlog: `13.534 → 517 lolos similarity → 517 lolos verifikasi teknis → 6 ditandai`. Angka
riil pertama dari pipeline lengkap (RDAP + blacklist + scoring kalibrasi T21) berjalan di atas
data produksi, bukan fixture. Disimpan ke `domain_findings`.

### Yang BELUM selesai — butuh satu aksi dari pemilik proyek

**T25 DoD ("brief terkirim ke Telegram otomatis, tiga hari berturut-turut") belum bisa dipenuhi
dalam satu sesi** — itu memang butuh waktu kalender nyata, bukan sesuatu yang bisa dipalsukan.

Yang memblokir pengiriman sungguhan: `SIAGA_OWNER_CHAT_ID` belum diketahui. Bot @siaga_ai_bot
sudah aktif dan polling (dikonfirmasi hidup lewat `channels status`), tapi belum ada pesan masuk
dari pemilik proyek untuk menangkap chat ID-nya (`getUpdates` kosong sepanjang sesi).

**Langkah berikutnya, begitu chat ID didapat:**
1. Isi `SIAGA_OWNER_CHAT_ID` di `.env`
2. Recreate container (`docker rm -f openclaw-gateway && bash scripts/run_openclaw.sh`) supaya
   env var baru terbawa — env var container bersifat tetap sepanjang hidup container
3. Job cron produksi (`siaga-daily-cycle`) sudah terjadwal `0 7 * * *` WIB, tidak perlu diubah lagi
4. Setelah itu, hitung mundur 3 hari berturut-turut sukses untuk menutup DoD T25 sepenuhnya

Cron job produksi dan seluruh kode pendukung (daily_brief.py, telegram_notify.py,
run_daily_cycle.py) sudah selesai dan teruji — yang tersisa murni menunggu satu input manusia
dan waktu kalender.
