# Devlog 02 September 2026 — Perbaikan Infrastruktur, Onboarding Agent, Aliran B

## Ringkasan

Sesi ini dimulai dari audit ulang status VPS setelah sesi sebelumnya menyimpang ke deployment
Vercel yang tidak diminta. Ditemukan bahwa Batch VPS lomba (Batch 1: 1-5 September 2026) hanya
memberi jendela 5 hari sebelum VM dinonaktifkan panitia — jauh lebih pendek dari asumsi awal
proyek (VPS aktif sepanjang periode lomba). Ini mengubah prioritas: footage video harus direkam
sebelum 5 September, dan collector lokal (bukan VPS) tetap jadi sumber data jangka panjang utama.

---

## 1. OpenClaw Gateway crash-loop (T11) — ditemukan dan diperbaiki

Gateway di VPS ternyata restart tanpa henti setiap ~10-20 detik sejak dipasang (restart counter
2280+ saat ditemukan). Akibatnya channel Telegram (Mode A / perintah interaktif) mati total —
`[telegram] channel autostart suppressed by crash-loop breaker`.

**Root cause** (ditemukan lewat `openclaw doctor`, bukan tebakan — sesuai aturan CLAUDE.md):
`OPENCLAW_SERVICE_REPAIR_POLICY=external` tidak diset di systemd unit, sehingga logika
self-respawn internal OpenClaw bentrok dengan `Restart=always` milik systemd.

**Perbaikan:** tambah env var tersebut ke `/etc/systemd/system/openclaw-gateway.service`,
restart, verifikasi `NRestarts=0` stabil, lalu `openclaw gateway call channels.start` untuk
memulihkan channel Telegram secara manual (breaker masih menahan autostart selama window 5 menit
setelah crash terakhir). Sekaligus set `commands.ownerAllowFrom` sesuai rekomendasi doctor.

## 2. Insiden: token Telegram sempat tercetak ke transkrip sesi

Saat men-diff `openclaw.json` untuk mencari akar masalah, token bot Telegram sempat tampil utuh
di output sebelum disensor pada percobaan berikutnya. Pengguna memutuskan **tidak merotasi**
token tersebut (keputusan eksplisit pengguna, bukan rekomendasi default). Dicatat di sini sebagai
bagian dari catatan kejujuran proyek, bukan disembunyikan.

## 3. OpenClaw workspace belum pernah di-onboarding

Ditemukan `IDENTITY.md` masih placeholder kosong, `BOOTSTRAP.md` belum dihapus (seharusnya
dihapus setelah first-run), nol penyebutan "siaga/phishing/fraud" di seluruh workspace agent.
Bot yang berjalan adalah asisten OpenClaw generik tanpa identitas proyek — signifikan karena
kategori lomba ini secara eksplisit menilai "penggunaan fitur AI hosting" (bobot 20%).

**Perbaikan:** `IDENTITY.md` (nama: SIAGA), `USER.md` (konteks proyek & pengguna), dan section
"Misi SIAGA" ditambahkan ke `AGENTS.md` (batasan keras: selalu "indikasi" bukan "terbukti", tidak
pernah mengarang angka, tidak eksekusi apa pun ke domain yang diperiksa). `TOOLS.md` diberi catatan
lingkungan (path repo, DB, catatan bahwa exec ke repo SIAGA belum diverifikasi end-to-end).

## 4. VPS crontab tidak menjalankan pipeline — cuma collector mentah

`run_daily_cycle.py` (pipeline + campaign clustering + brief Telegram) ada di repo VPS tapi
**tidak pernah masuk crontab**. Hanya collector mentah, healthcheck, dan backup yang terjadwal.
`domain_findings` di VPS berisi 548 baris — hasil satu kali jalan manual (saat migrasi T10),
bukan proses harian berkelanjutan. Ditambahkan entri cron baru: `45 6 * * *` (15 menit setelah
collector), belum diverifikasi lewat siklus otomatis penuh — cek besok pagi.

## 5. Aliran B — rancangan awal terbukti tidak bisa dibangun, dipivot

CLAUDE.md dan `plan/` sejak awal menyatakan Aliran B (TLD global: `.xyz`, `.top`, `.online`, dll)
wajib ada karena penipu nyata jarang pakai `.co.id` (butuh dokumen legal). Belum pernah dibangun
sampai sesi ini. Tiga jalur diverifikasi lewat request nyata (bukan tebakan):

| Jalur | Hasil |
|---|---|
| `ctlogs.dev` endpoint TLD-wide | **Tidak ada.** Hanya exact-domain, subdomains-of-a-domain, org search, serial, SPKI. Bare TLD (`xyz`) ditolak validasi hostname. |
| `crt.sh` JSON API (`?q=%25brand%25`) | 502 Bad Gateway konsisten (3x percobaan) |
| `crt.sh` Postgres publik (`guest@crt.sh:5432`) | Konek berhasil, tapi query timeout/putus tidak menentu |
| CertStream firehose | Layanan publik gratis (`certstream.calidog.io`) sudah mati; pengganti (`certstream.dev`) cuma software self-host, butuh server nyala 24/7 |

**Kesimpulan:** tidak ada layanan gratis untuk "pantau semua sertifikat baru di TLD X" secara
andal. Desain awal di `plan/` tidak realistis dengan constraint jaringan proyek ini.

**Pivot (diimplementasikan, `collector/ct_collector_b.py`):** generate kandidat typosquat dari
214 stem watchlist (exact + 6 modifier umpan phishing x 2 TLD murah = 2.688 kandidat), cek satu
per satu ke endpoint `/v1/domain/{hostname}` yang TERBUKTI berfungsi (exact-domain lookup). Mirip
teknik dnstwist. Match pertama yang ditemukan saat uji: `adakami.xyz` (official domain AdaKami
sebenarnya `adakami.id`) — sertifikat sejak Juli 2025, layak diperiksa Tahap 2/3.

**Bug ditemukan & diperbaiki di percobaan pertama:** HTTP 429 (rate limit) tidak ditangani,
membuat seluruh run mati dalam <1 menit dengan 0 hasil dari 2.688 kandidat, bukan diperlakukan
sebagai error per-kandidat. Diperbaiki dengan exception `RateLimited` terpisah, backoff+retry
per kandidat, dan penghentian dini kalau server terus menolak beruntun (bukan menggerus ribuan
kandidat yang pasti gagal semua). 17 test baru di `tests/test_ct_collector_b.py`, termasuk
regression test spesifik untuk bug 429 ini.

## 6. Aliran B — eksekusi penuh, dua bug operasional lagi, hasil nyata

Percobaan run penuh (2.688 kandidat) pertama mati dalam <1 menit karena bug 429 di atas.
Percobaan kedua berjalan ~3 jam nyaris tanpa progres: laptop kehilangan jaringan ~2 jam di
tengah jalan, dan `getaddrinfo` Windows tidak menghormati `timeout` urllib saat adapter jaringan
reconnect — proses macet diam tanpa error selama 15+ menit, harus di-kill manual.

**Perbaikan:** `socket.setdefaulttimeout()` sebagai lapisan kedua, plus `MAX_RUN_SECONDS` (110
menit) sebagai batas keras seluruh run. Percobaan ketiga selesai bersih: **2.508/2.688 kandidat
dicek, 108 domain ditemukan punya sertifikat nyata**, 0 error (jaringan stabil kali ini). Sisa
180 kandidat berhenti aman kena batas waktu — akan tercakup di run berikutnya, bukan hilang
permanen (beda dengan Aliran A yang punya window 24 jam sekali jalan).

Contoh temuan nyata dari Aliran B (bukan domain resmi institusi terkait):
`telkomsel.top`, `maybank.top`, `shopee.top`, `shopeepay.xyz`, `dana.top`, `dana.xyz`,
`linkaja.top`. Lewat pipeline T22: 105/108 lolos Tahap 1 (97%), semua mendarat di skor 40
(watchlist_similarity 25 + risky_tld 15 — domain-domain ini sudah agak lama, bukan baru
terdaftar, jadi sinyal domain_age tidak ikut menyala; ini perilaku skoring yang benar, bukan bug).

## 7. LLM mati total — model provider di-deprecate, ditemukan & diperbaiki

Saat verifikasi Tahap 3, ditemukan **LLM sama sekali tidak berhasil dipanggil** sejak beberapa
hari terakhir (data usage sukses terakhir: 29 Agustus). Error asli provider (`api.justwoker.icu`):

```
model_not_found: "No available channel for model claude-opus-4-8-thinking under group default"
```

Model yang dikonfigurasi sudah tidak disediakan provider. Dicek `/v1/models` (dengan User-Agent
yang benar — endpoint ini sempat menolak dengan 403 Cloudflare code 1010 pakai UA default urllib)
dan hanya tersisa dua model: `claude-opus-5` dan `claude-opus-5-thinking`. Keduanya dites langsung
lewat `complete()` dan berhasil. `.env` lokal diupdate ke `claude-opus-5` (non-thinking, lebih
hemat token untuk tugas klasifikasi terstruktur ini). **Diverifikasi ulang di dua jalur:**
- Mode A (`lib.scoring.analyze_message`): linguistic analysis LLM berhasil, hasil koheren
  (urgency=2, false_authority=2, dangerous_request=['otp'] untuk pesan phishing BCA contoh).
- Mode B (`lib.pipeline`): LLM synthesis tetap tidak terpanggil untuk 108 temuan Aliran B karena
  memang tidak ada yang mencapai ambang risk_score>=60 (by design, bukan karena LLM rusak).

**Belum diterapkan di VPS** — lihat blocker di bawah.

## 9. Cron lokal `siaga-daily-cycle` sama rusaknya, plus konflik Telegram lokal-vs-VPS

Ternyata OpenClaw lokal (`docker exec openclaw-gateway`) sudah punya cron `siaga-daily-cycle`
(07:00 WIB) sejak awal -- tapi statusnya **error 7x berturut-turut**, dengan error yang SAMA
persis (`claude-opus-4-8-thinking` deprecated). Root cause lebih dalam: cron ini berjenis
"agent-prompt cron" (menyuruh agent LLM menjalankan skrip via exec) bukan "command cron" langsung
-- begitu model mati, cron ini bahkan tidak bisa MULAI, apalagi menjalankan skrip yang sebenarnya
tidak butuh LLM sama sekali (`run_daily_cycle.py` kirim Telegram sendiri lewat `lib/telegram_notify.py`).

Dihapus dan dibuat ulang sebagai **command cron job** (`openclaw cron add --command "..."`,
saran `openclaw doctor` sendiri) -- deterministik, tidak bergantung LLM sama sekali, konsisten
dengan prinsip project yang sudah ada (`lib/telegram_notify.py` sengaja bypass OpenClaw routing).
Ditemukan dua bug tambahan saat verifikasi jalan penuh:
- `ModuleNotFoundError: psutil` -- venv container tidak punya dependency ini terpasang (container
  sudah uptime 4 hari, requirements.txt kemungkinan ditambah `psutil` setelah bootstrap terakhir).
  Diperbaiki manual (`pip install --user`), tapi **ephemeral** -- hilang kalau container di-restart,
  karena bootstrap dependency di `run_openclaw.sh` cuma jalan sekali saat `docker run`, bukan setiap
  container restart otomatis (`--restart unless-stopped`). Catatan untuk perbaikan permanen nanti.
- Path `/workspace/siaga` rusak jadi `C:/Program Files/Git/workspace/siaga` -- Git Bash Windows
  otomatis mengonversi path absolut Unix di argumen CLI. Perbaikan: `MSYS_NO_PATHCONV=1`.

Setelah kedua fix, test run **berhasil (`status: ok`)** -- brief harian ter-generate dengan benar
untuk data 2026-09-02.

Terpisah, ditemukan **local dan VPS openclaw-gateway saling bentrok** memakai token Telegram yang
sama (`Conflict: terminated by other getUpdates request`), membuat keduanya flap/restart berulang.
Channel Telegram di instance lokal dimatikan (`channels.telegram.enabled: false` + restart
container) supaya tidak lagi mengganggu VPS begitu SSH pulih. Model agent lokal juga diperbaiki ke
`claude-opus-5` (config `agents.defaults.model.primary` dan `models.providers.openai.models[0].id`)
untuk konsistensi, meski channel-nya sekarang nonaktif.

## 10. Bug ketiga ditemukan lewat cron run yang sama: URLhaus API wajib Auth-Key

Log run cron di atas menunjukkan `Blacklist check failed: HTTP Error 401` untuk SETIAP domain
yang dicek. Dites langsung ke `urlhaus-api.abuse.ch` -- benar, abuse.ch sudah mewajibkan header
`Auth-Key` untuk semua akses API (perubahan eksternal, bukan bug lama). Tidak pernah membahayakan
skoring (modul ini sudah fail-safe ke UNKNOWN sejak awal), tapi jadi buta total dan membanjiri log
dengan 401 per domain. `lib/blacklist_check.py` diperbaiki: baca `URLHAUS_AUTH_KEY` dari `.env`,
dan kalau belum diset, langsung lapor jujur "tidak dapat diperiksa" tanpa mencoba request yang
pasti gagal. **Butuh tindakan pengguna**: daftar gratis di https://auth.abuse.ch/ untuk dapat key.

## Blocker mendesak: SSH ke VPS mati

Setelah insiden jaringan lokal, SSH ke VPS (port 4422) mulai timeout terus-menerus, padahal
ping ke VPS normal (~30ms) — VM hidup, tapi service SSH atau firewall tidak merespons di port
itu. Tidak bisa didiagnosis/diperbaiki tanpa akses console panitia (CloudBaik), yang hanya bisa
dilakukan pengguna. Menghalangi: sync `ct_collector_b.py` + fix `.env` LLM_MODEL ke VPS, dan
verifikasi cron `run_daily_cycle.py` yang baru ditambahkan (harusnya jalan pertama kali 06:45 WIB
besok, tidak bisa dicek dari sini kalau SSH belum pulih).
